# Modèle de domaine et schéma

- **Statut** : acceptée
- **Date** : 2026-09-09
- **Ticket** : [Modèle de domaine et schéma Drizzle](https://github.com/Bryan21B/scoring-sheets/issues/15), sous la carte [Carte — feuille de score multi-appareils pour 6 qui prend, Uno et Dnup](https://github.com/Bryan21B/scoring-sheets/issues/1)

## Ce document ne contient pas de code

La destination de la carte s'arrête à la spec : elle ne produit pas de code
applicatif. Ce document dit donc **tout ce dont `src/db/schema.ts` a besoin** —
tables, colonnes, clés, contraintes, déclencheurs, index — sans l'écrire.

Écrire `schema.ts`, lancer `bun run db:generate` et étendre `tests/unit/db.test.ts`
pour attester le jeu de migrations est le **premier ticket du lot
d'implémentation**, que la carte a toujours posé comme un geste à part. Le faire
maintenant reviendrait à commiter du SQL avant que
[Design doc consolidé, CONTEXT.md et ADR](https://github.com/Bryan21B/scoring-sheets/issues/16) n'ait figé les noms.

`drizzle/` ne s'édite jamais à la main, et `.claude/settings.json` l'interdit.

## Les tables

### `joueur`

Le roster global. Un joueur est persistant entre parties, son nom est modifiable
et **n'est pas unique** : un doublon se désambiguïse dans l'interface.

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | monotone |
| `nom` | TEXT NOT NULL | modifiable, non unique |
| `cree_le` | INTEGER NOT NULL | horloge serveur |

### `appareil`

Le navigateur d'une personne, reconnu par un cookie serveur `HttpOnly` de 400
jours réémis à chaque requête. Le lien vers un joueur est **global**, jamais par
partie, et c'est une **déclaration, pas une preuve**.

| Colonne | Type | Notes |
|---|---|---|
| `id` | TEXT PK | la valeur opaque du cookie |
| `joueur_id` | INTEGER NOT NULL → `joueur` | plusieurs appareils peuvent pointer le même joueur |
| `vu_le` | INTEGER NOT NULL | dernière requête |
| `cree_le` | INTEGER NOT NULL | |

Repointer un appareil ne relit **jamais** le passé : le journal fige le joueur
agissant à l'écriture, précisément pour ça.

### `partie`

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | monotone — c'est lui qui départage l'ordre de rejeu |
| `code` | TEXT NOT NULL UNIQUE | six caractères Crockford Base32 |
| `jeu_id` | TEXT NOT NULL | id de catalogue, **aucune clé étrangère** |
| `regles` | TEXT NOT NULL | instantané JSON des règles **résolues** |
| `version` | INTEGER NOT NULL DEFAULT 0 | estampille de poll |
| `fin_le` | INTEGER NULL | date de la fin |
| `fin_cause` | TEXT NULL | `terminee` ou `abandonnee` |
| `fin_par` | INTEGER NULL → `joueur` | qui a clos ou abandonné |
| `cree_le` | INTEGER NOT NULL | |

**Pas de table `jeux`.** Le catalogue vit dans une constante TypeScript, éditable
sans migration ; `jeu_id` est validé par Zod à l'écriture. Le relâchement est
assumé : une écriture directe en base pourrait y mettre n'importe quoi, à dix
utilisateurs qui n'y ont pas accès.

**Une fin, absente ou présente.** `CHECK ((fin_le IS NULL) = (fin_cause IS NULL))`
et `fin_cause IN ('terminee','abandonnee')`. Il n'y a pas de statut à trois
valeurs : pas de `fin_le`, la partie est en cours. La **reprise** efface les trois
colonnes.

**Le seuil surchargé n'a pas de colonne** : il est déjà appliqué dans
l'instantané.

**Le code n'a besoin d'aucun registre pour n'être jamais recyclé.** Sur un
milliard de combinaisons, retomber sur celui d'une partie supprimée en salle
d'attente est un événement qui n'arrivera pas.

### `participant`

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | l'ordre d'insertion **est** l'ordre de table |
| `partie_id` | INTEGER NOT NULL → `partie` | |
| `joueur_id` | INTEGER NOT NULL → `joueur` | |
| `retire_le` | INTEGER NULL | le joueur qui s'en va |

`UNIQUE (partie_id, joueur_id)`.

Un participant peut n'avoir **aucun appareil** : le créateur a le droit d'ajouter
des joueurs pour eux. Un participant **retiré** garde ses valeurs, sort de la
complétude des manches suivantes et du classement final.

### `manche`

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `partie_id` | INTEGER NOT NULL → `partie` | |
| `numero` | INTEGER NOT NULL | jamais réutilisé |
| `close_le` | INTEGER NULL | la clôture est **déclarée**, pas déduite |
| `close_par` | INTEGER NULL → `joueur` | |

`UNIQUE (partie_id, numero)` — c'est cette contrainte qui fait que deux téléphones
ouvrant « la manche suivante » en même temps **rejoignent la même**.

Supprimer une manche laisse un **trou** : la suivante est le plus grand numéro
plus un.

### `saisie`

Une ligne **est** une *case* du glossaire. Le mot `case` étant réservé en SQL, la
table porte le nom du geste qui la crée.

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `manche_id` | INTEGER NOT NULL → `manche` | ON DELETE CASCADE |
| `joueur_id` | INTEGER NOT NULL → `joueur` | le joueur **concerné**, jamais l'auteur |
| `valeur` | INTEGER NULL | ce qui a été saisi |

`UNIQUE (manche_id, joueur_id)`, `CHECK (valeur IS NULL OR valeur >= 0)`.

**Le grain est imposé par l'écriture concurrente**, pas seulement par les manches
partielles : la politique de conflit exige que deux joueurs écrivant des cases
différentes ne se marchent jamais dessus, ce qu'un objet JSON par manche rendrait
impossible puisque ce serait la même ligne.

**Une seule colonne, dont le mode donne le sens.** Le mode vit dans l'instantané
de règles et gouverne déjà la complétude et le gagnant de manche ; lui confier
aussi la lecture de cette colonne n'ajoute aucun concept.

| Mode | Ce que `valeur` porte | Combien de lignes |
|---|---|---|
| `entierParJoueur` | l'entier saisi | une par participant actif |
| `sommeAuGagnant` | le **total unique** crédité au gagnant | **une seule**, celle du gagnant |
| `podium` | le **rang** (1, puis 2) | deux |

**Une ligne existe dès que la case est touchée**, et `valeur IS NULL` veut dire
*touchée mais vide* — l'état qu'Uno traverse entre désigner le sorti et taper son
total. La politique de conflit sait déjà le traiter : le vide y est une valeur.

À `sommeAuGagnant`, **la ligne est la désignation** : le gagnant est celui qui en
a une.

### `journal`

Append-only, jamais modifié, jamais purgé.

| Colonne | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `partie_id` | INTEGER NOT NULL → `partie` | sûr : une partie ne se supprime que journal vide |
| `geste` | TEXT NOT NULL | les sept gestes |
| `joueur_agissant_id` | INTEGER NOT NULL → `joueur` | **figé à l'écriture** |
| `appareil_id` | TEXT NULL → `appareil` | gardé à côté du joueur |
| `manche_numero` | INTEGER NULL | **un entier nu, sans clé étrangère** |
| `joueur_concerne_id` | INTEGER NULL → `joueur` | |
| `detail` | TEXT NULL | JSON |
| `ecrit_le` | INTEGER NOT NULL | horloge **serveur** |

**Le journal ne peut porter aucune clé étrangère vers une manche.** Une manche se
supprime, et le journal ne se modifie jamais : une cascade le violerait, un
`ON DELETE SET NULL` aussi. Il garde donc le **numéro** de la manche, pas son id,
ce qui a le mérite d'être ce qu'un humain lit.

**Les champs communs en colonnes, le variable en JSON.** On filtre et on trie sur
le geste, l'auteur, l'horloge et la case ; on ne fait que **montrer** les
anciennes et nouvelles valeurs, et la liste des valeurs qu'une suppression de
manche emporte — liste de longueur variable, donc JSON par nature.

Une suppression de manche à cinq joueurs reste **une** ligne.

## Ce qui est stocké, et ce qui est calculé

| Stocké | Calculé |
|---|---|
| les saisies | les totaux |
| la clôture d'une manche, avec sa date | la complétude d'une manche |
| la fin d'une partie, avec sa date et sa cause | le gagnant d'une manche |
| le retrait d'un participant | le classement, en groupes de rang |
| l'instantané de règles | le gel de la liste des participants |
| l'estampille de version | les manches jouées et gagnées |
| le journal | le taux de victoires, et la note plus tard |

**Rien de ce qui se recalcule n'est stocké**, à une exception délibérée : la fin
d'une partie.

### Pourquoi la fin est estampillée

Le cycle de vie avait posé « terminée est dérivée ». En dessinant les index, le
coût apparaît : savoir si une partie est terminée demanderait de faire tourner le
moteur, donc de charger toutes ses manches et toutes ses saisies. L'historique et
le palmarès ne seraient alors **pas des requêtes SQL** mais des replis applicatifs
sur l'intégralité de la base, qu'aucun index n'accélère.

Ce qui tranche : **l'écriture qui clôt la manche calcule déjà `fini`**, puisqu'il
lui faut décider si elle montre l'écran de fin. L'estampiller là ne coûte rien, et
ce n'est pas stocker un calcul continu — c'est enregistrer un **événement
ponctuel**, exactement ce que la clôture d'une manche fait déjà.

Le **scellement** interdisant toute modification ensuite, la valeur stockée ne
peut jamais diverger du calcul.

## Les invariants, et de quel côté ils tombent

**Le schéma les tient seul :**

- l'unicité de la manche par partie et numéro ;
- l'unicité de la saisie par manche et joueur ;
- l'unicité du participant par partie et joueur ;
- l'unicité du code de partie ;
- le plancher de zéro sur une saisie, que les trois modes partagent ;
- la cohérence de la fin, par `CHECK` ;
- l'**append-only du journal**, par deux déclencheurs qui refusent toute mise à
  jour et toute suppression.

**Ils restent applicatifs :**

- les **bornes hautes par jeu** — elles vivent dans l'instantané de règles, en
  JSON et propre à chaque partie, donc aucune contrainte ne les voit ;
- le **scellement**, la **complétude**, le **gel** — tous dépendent d'un calcul ;
- l'**écriture conditionnelle**, qui est une clause `WHERE` sur la mise à jour,
  donc atomique sans être une contrainte.

Ce qui reste applicatif passe par **Zod à la frontière externe**, comme
`AGENTS.md` l'impose déjà.

### L'estampille de version tient par déclencheur

Elle doit s'incrémenter à **chaque** écriture d'une partie, faute de quoi les
autres téléphones servent du périmé sans que rien ne proteste. Une incrémentation
oubliée dans une Server Action est invisible en développement et fatale à table.

Des déclencheurs sur `manche`, `saisie`, `participant` et `journal` la portent,
comme ils portent déjà l'append-only : le même mécanisme, pour la même raison.

## Les index

| Index | Ce qu'il sert |
|---|---|
| `partie(code)` unique | l'arrivée par lien, et le poll de version |
| `partie(fin_le DESC) WHERE fin_le IS NOT NULL` | l'ordre de l'historique, et le rejeu de la note |
| `partie(jeu_id)` | le filtre par jeu de l'historique |
| `manche(partie_id, numero)` unique | la feuille de score, et « la manche suivante » |
| `saisie(manche_id, joueur_id)` unique | l'écriture conditionnelle d'une case |
| `participant(partie_id, joueur_id)` unique | le gel, et la lecture d'une tablée |
| `participant(joueur_id)` | la fiche de joueur et ses compteurs |
| `journal(partie_id, ecrit_le DESC)` | le tiroir des corrections |
| `appareil(joueur_id)` | le rattachement d'un appareil |

L'index partiel sur `fin_le` est ce qui rend l'historique et le palmarès
ordinaires : sans l'estampillage de la fin, il n'existerait pas.

document, lancer `bun run db:generate`, commiter le SQL généré sans le toucher,

fichier nomme déjà le mode de défaillance à attraper, une édition de schéma sans

fraîche.
